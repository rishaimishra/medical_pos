1. DATABASE ARCHITECTURAL FOUNDATION & DESIGN PRINCIPLES
--------------------------------------------------------------------------------
The database layer for the Medical POS and Pharmacy Management System is engineered
for zero-latency retail checkout, clinical regulatory compliance (Schedule H/H1, GST),
and high-concurrency multi-user operations.

1.1 Core Engineering Principles:
    - ACID Compliance: All checkout sales, purchase order receipts, and return processing
      must execute inside atomic database transactions (`START TRANSACTION` ... `COMMIT`).
      Any failure rolls back all inventory and payment records completely.
    - Strict Financial Precision: Monetary values, taxable base values, and tax amounts
      use `DECIMAL(12,2)` or `DECIMAL(10,2)`. GST percentages use `DECIMAL(5,2)`. Floating
      point data types (`FLOAT`, `DOUBLE`) are strictly prohibited for currency.
    - Foreign Key Integrity: Relational referential integrity enforces constraints between
      medicines, batches, sales, and line items. Master drug deletion is blocked if active
      batches exist.
    - Audit Trail Preservation: Inventory adjustments, price changes, and returns write
      immutable append-only audit rows (`stock_adjustments`, `customer_purchase_log`).
    - Character Set & Collation: Standardized on `utf8mb4` with `utf8mb4_unicode_ci` to
      support international drug compositions, supplier names, and currency symbols (`₹`).
    - Dual Storage & Migration Pipeline: Supports direct SQL relational storage (MySQL /
      PostgreSQL / SQLite) with automated schema self-healing, plus JSON import/export
      for offline backups and historical data migrations.

Table 1: `settings` (System Configuration & Store Metadata)
    - Purpose: Stores store profile, licensing, tax defaults, and communication credentials.
    - Columns:
      * `id`              INT AUTO_INCREMENT PRIMARY KEY
      * `store_name`      VARCHAR(255) NOT NULL DEFAULT 'Medical POS Pharmacy'
      * `store_address`   TEXT
      * `store_phone`     VARCHAR(50)
      * `store_email`     VARCHAR(255)
      * `store_gst`       VARCHAR(50)  COMMENT 'Store GSTIN / Tax Identification'
      * `store_dl`        VARCHAR(50)  COMMENT 'Drug License Number (DL No)'
      * `currency`        VARCHAR(20)  DEFAULT '&#8377;' COMMENT 'HTML entity or symbol'
      * `low_qty`         INT          DEFAULT 10 COMMENT 'Threshold for low-stock alert'
      * `expiry_days`     INT          DEFAULT 90 COMMENT 'Days threshold for near-expiry alert'
      * `email_provider`  VARCHAR(20)  DEFAULT 'sendgrid' COMMENT 'sendgrid or smtp'
      * `sendgrid_key`    VARCHAR(255) COMMENT 'SendGrid v3 REST API key'
      * `smtp_host`       VARCHAR(255)
      * `smtp_port`       INT          DEFAULT 587
      * `smtp_user`       VARCHAR(255)
      * `smtp_pass`       VARCHAR(255)
      * `smtp_from`       VARCHAR(255)
      * `smtp_name`       VARCHAR(255)
      * `smtp_secure`     VARCHAR(10)  DEFAULT 'tls'
      * `setup_done`      TINYINT(1)   DEFAULT 0 COMMENT '1 if first-run wizard completed'
      * `setup_step`      INT          DEFAULT 1 COMMENT 'Server-side wizard step recovery (1-4)'
      * `setup_token`     VARCHAR(100) COMMENT 'Device session token for wizard auto-resume'
      * `setup_otp`       VARCHAR(10)  COMMENT '6-digit email OTP for cross-device wizard unlock'
      * `setup_otp_exp`   DATETIME     COMMENT 'OTP expiration timestamp'
      * `storage`         VARCHAR(20)  DEFAULT 'postgres' COMMENT 'Storage engine flag: postgres/mysql/json'
      * `updated_at`      DATETIME
      * `created_at`      DATETIME

      * `branch_id`       INT          COMMENT 'NULL for global all-branch access within store_id; ID for assigned branch'
      * `active`          TINYINT(1)   DEFAULT 1

      * `created_at`      DATETIME

১. ডেটাবেস আর্কিটেকচারাল ভিত্তি ও ডিজাইন নীতিমালা (DATABASE ARCHITECTURAL FOUNDATION & DESIGN PRINCIPLES)
--------------------------------------------------------------------------------
মেডিকেল POS এবং ফার্মেসি ম্যানেজমেন্ট সিস্টেমের ডেটাবেস স্তরটি অতি-দ্রুত রিটেইল চেকআউট,
ক্লিনিক্যাল রেগুলেটরি কমপ্লায়েন্স (Schedule H/H1 ড্রাগ অডিট, GST ট্যাক্সেশন) এবং উচ্চ-কনকারেন্সি
মাল্টি-ইউজার অপারেশনের জন্য বিশেষভাবে ডিজাইন করা হয়েছে।

১.১ মূল ইঞ্জিনিয়ারিং নীতিমালা:
    - ACID কমপ্লায়েন্স (ACID Compliance): সকল সেলস চেকআউট, পারচেজ অর্ডার রিসিভিং এবং
      রিটার্ন প্রসেসিং অবশ্যই অ্যাটমিক ডেটাবেস ট্রানজ্যাকশনের (`START TRANSACTION` ... `COMMIT`)
      মধ্যে সম্পাদিত হবে। কোনো পর্যায়ে ব্যর্থতা ঘটলে ইনভেন্টরি স্টক ও পেমেন্ট রেকর্ড সম্পূর্ণ রোলব্যাক হবে।
    - কঠোর আর্থিক নির্ভুলতা (Strict Financial Precision): সমস্ত মুদ্রাগত মান, ট্যাক্সেবল বেস
      এবং ট্যাক্স পরিমাণের জন্য `DECIMAL(12,2)` বা `DECIMAL(10,2)` ব্যবহৃত হবে। জিএসটি
      শতকরা হারের জন্য `DECIMAL(5,2)`। আর্থিক বা কারেন্সি ফিল্ডে ফ্লোটিং পয়েন্ট ডেটা টাইপ
      (`FLOAT`, `DOUBLE`) ব্যবহার সম্পূর্ণ নিষিদ্ধ।
    - ফরেন কি ইন্টিগ্রিটি (Foreign Key Integrity): ওষুধ, ব্যাচ, সেলস এবং লাইন আইটেমের মধ্যে
      রেফারেন্সিয়াল ইন্টিগ্রিটি নিয়ম প্রয়োগ করা হবে। সক্রিয় ব্যাচ বর্তমান থাকলে মূল ওষুধ
      মুছে ফেলা (Delete) প্রতিহত করা হবে (Restrict Rule)।
    - অডিট ট্রেইল সংরক্ষণ (Audit Trail Preservation): স্টক সমন্বয়, মূল্য পরিবর্তন এবং
      পণ্য ফেরতের জন্য অপরিবর্তনযোগ্য অ্যাপেন্ড-অনলি অডিট রেকর্ড বজায় রাখা হবে (`stock_adjustments`,
      `customer_purchase_log`)।
    - ক্যারেক্টার সেট ও কোলেশন (Character Set & Collation): আন্তর্জাতিক ওষুধের রাসায়নিক
      কম্পোজিশন, সরবরাহকারীর ঠিকানা এবং মুদ্রা প্রতীক (`₹`) ত্রুটিহীনভাবে সংরক্ষণের জন্য
      `utf8mb4` ও `utf8mb4_unicode_ci` প্রমিত করা হয়েছে।
    - ডুয়াল স্টোরেজ ও মাইগ্রেশন পাইপলাইন (Dual Storage & Migration Pipeline): স্বয়ংক্রিয়
      স্কিমা সেলফ-হিলিং সহ সরাসরি রিলেশনাল এসকিউএল স্টোরেজ (MySQL / PostgreSQL / SQLite)
      এবং অফলাইন ব্যাকআপ ও হিস্টোরিক্যাল ডেটা কনভার্শনের জন্য JSON ইমপোর্ট/এক্সপোর্ট পাইপলাইন সমর্থিত।
